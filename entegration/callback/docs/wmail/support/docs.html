Single Sign-On (SSO) Integration

"Sign in with Wmail" uses a standard OAuth 2.0 authorization-code flow — similar to "Sign in with Google" or Entra ID (Azure AD).

Nothing about a user's identity is ever sent to your redirect URL until Wmail has verified, server-side, that the URL belongs to your registered application.

1

Register your application

In the Developer Panel, click Register Application and give it a name plus one or more exact redirect URIs — the page on your site that Wmail is allowed to send users back to (e.g., https://myapp.com/auth/wmail/callback).

You will receive:

  • client_id: Public, safe to include in frontend code.
  • client_secret: Private — keep it strictly on your server (shown once).

Wmail will refuse to redirect anywhere that isn't on this exact list, so double- and triple-check it before saving.

2

Send the user to Wmail to sign in

Redirect the user's browser to the login page with your client_id, the exact redirect_uri you registered, and a random state value.

Note: Store the state parameter (e.g., in a cookie) so you can verify it on return. This prevents Cross-Site Request Forgery (CSRF) on your callback handler.

3

User signs in and approves

The user logs into their Wmail identity as usual, then sees a consent screen naming your app and the requested permissions (name + email).

Only after clicking Allow does Wmail redirect back to your redirect_uri with a short-lived, single-use code and your state parameter attached in the query string.

4

Exchange the code for the user's identity

On your callback route, first verify that the returned state matches what you stored in Step 2. Then, call the token endpoint directly from your backend (never from the browser — this request requires your client_secret): 

POST /oauth/token
Host: wmail.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&client_id=YOUR_CLIENT_ID
&client_secret=YOUR_CLIENT_SECRET
&redirect_uri=YOUR_REDIRECT_URI
&code=AUTHORIZATION_CODE

⚠️ Security Notes

  • Exact URI Matching: redirect_uri must match exactly what you registered — no wildcards or "starts with" matching allowed. If you need alternate environments (staging, localhost), register them as separate URIs.
  • Keep Secrets Private: client_secret is a server-side secret. Never bundle it into frontend JavaScript, mobile apps, or public repositories.
  • Short-Lived Authorization Code: The authorization code is single-use and expires after 2 minutes — always exchange it immediately within your callback handler.
  • State Verification: Always verify the state parameter on your callback route before trusting the response payload.
